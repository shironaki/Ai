# Контракт моста

Один файл на два репозитория. Правится **осознанно и сразу в обоих**: если
одна сторона поменяет конверт, а вторая нет — мост замолчит, и это будет
выглядеть как «сестра не отвечает».

## Формат

Одна строка, начинающаяся с `AI-BRIDGE1 `, дальше JSON:

```
AI-BRIDGE1 {"v":1,"id":"…","ts":1794293239501,"ttl":60000,"tool":"__context","args":{},"actor":"5","chat":"5","chatType":"private","sig":"…"}
```

- `id` — уникальный; повтор такого же `id` отвергается (защита от повтора).
- `ts` + `ttl` (60 с) — свежесть: просроченный конверт не исполняется.
- `sig` — HMAC-SHA256 по каноническому JSON (сортированные ключи, без `sig`).
- `chatType` входит в подпись: групповое умение нельзя выдать за личное.

## Подпись словами

Перед конвертом может стоять строка для человека:

```
🤍 Аи → Юи · что известно о человеке · чат 5
AI-BRIDGE1 {…}
```

Она **вне** подписи и не меняет конверт. Разбор ищет префикс в любом месте
строки. Ответ с пояснением отправляется только если в вопросе оно было —
сердце старой сборки разбирает конверт с начала строки.

## Служебные умения

| Умение | Что делает |
|---|---|
| `__catalog` | что этот бот умеет в этом чате и для этой роли |
| `__context` | что известно о человеке: роль, уровень, VIP, варны, владелец |

`__context` отдаёт **только** эти поля. Ни истории, ни текстов сообщений, ни
личных данных. `context_unavailable` — честный отказ, а не пустой ответ.

## События

Обратный поток: бот замечает — сердце говорит. Виды: `member_joined`,
`game_finished`, `level_up`, `reminder`. Новый вид добавляется сначала в
список принимающей стороны, иначе он молча игнорируется.

## Правила изменения

1. Новая форма конверта → поднять `BRIDGE_VERSION` и обновить обе стороны.
2. Новое умение → сначала приёмник, потом отправитель. Обратный порядок даёт
   «нет в этом чате» на живом боте.
3. Секрет никогда не едет в конверте: канал читают люди.
4. Тест контракта лежит в обоих репозиториях и должен проходить с одним
   секретом: `0123456789abcdef0123456789abcdef`.
