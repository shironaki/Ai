# Дом на телефоне: автопубликация и будильник

Второй телефон заменяет GitHub Actions целиком. Один скрипт, один процесс:

- **публикует сам.** Раз в три минуты смотрит в ветку. Появилась новая сборка —
  гоняет тесты, репетирует в облаке и публикует. Упало что-то из этого — бот
  остаётся на прежней сборке, владельцу приходит одна строка, почему;
- **будит сердце.** Раз в минуту, чтобы напоминания, утренняя сводка и
  отложенные ответы приходили без единого сообщения от людей.

Минуты Actions не тратятся: workflow `Heart` теперь только кнопка на случай,
когда телефона под рукой нет.

> Проверено: логика скрипта — тестами на подставных инструментах; живой
> прогон в Linux с настоящими git, gh, npm и настоящим инструментом
> публикации — от клонирования поверх старой папки до границы платформы
> (проверка, файл ключей, тесты, ключи в код и обратно, обновление самого
> скрипта из GitHub). На телефоне владельца (Termux, node 24) 13.11.2026
> `check` прошёл целиком, включая платформу и бота-будильника; в тот же день
> телефон сам опубликовал 0.23.0 — владелец подтвердил: «Аи обновилась».

## 1. Поставить (Termux, один раз)

```bash
pkg update -y && pkg install -y git gh nodejs-lts curl nano
gh auth login
gh repo clone shironaki/Ai ~/Ai
```

Так ставится `main` — последняя слитая сборка. Пока PR #28 не слит, этого
скрипта в `main` ещё нет: тогда к третьей строке дописать
` -- --branch arena/95ac5a16-ai`.

Termux — из F-Droid: версия из Google Play давно не обновляется.

**Если папка `~/Ai` на телефоне уже есть** (осталась от прежних попыток),
третья строка остановится словами `destination path … already exists`, а
скрипта в старой папке не окажется: `scripts/phone.sh: No such file or
directory`. Старую папку не стирайте — отодвиньте и повторите клонирование:

```bash
cd ~ && mv Ai Ai-old
gh repo clone shironaki/Ai ~/Ai
```

Когда всё заработает, `~/Ai-old` можно удалить: `rm -rf ~/Ai-old`.

## 2. Файл ключей `~/.heart.env`

Ключи лежат только на телефоне, вне репозитория. Создавать файл руками не
нужно: первая проверка (раздел 3) сама положит пустой, с готовыми именами.
Остаётся вписать значения — сразу после «=», без кавычек:

```bash
nano ~/.heart.env
```

В nano: вставить — долгое нажатие на экран, сохранить — Ctrl+O и Enter,
выйти — Ctrl+X.

```
TGCLOUD_HEART_TOKEN=
AI_PROVIDER_KEY=
OWNER_TG_ID=
HEART_BRANCH=arena/4d5d41a1-ai
# KEY_GIGACHAT=
# KEY_EXPLABS=
# KEY_CLOUDFLARE=
# ALARM_BOT_TOKEN=
# ALARM_CHAT_ID=
```

`HEART_BRANCH` — ветка, за которой следит телефон: пока идёт рабочий чат —
его ветка (здесь — нынешнего чата, с 16.11.2026), между чатами — `main`. Как её
менять — раздел 9. **Ветка первого чата (`arena/95ac5a16-ai`) больше не
обновляется**: пока в файле стоит она, новые сборки до бота не доходят
(17.11.2026 сборка 0.36.0 так и не была опубликована).

Строка с «#» в начале не читается: чтобы включить её, «#» убирают. Русские
слова или пробелы после «=» скрипт ключом не считает и в бота не отправляет —
скажет, какая строка не похожа на ключ.

GitHub секреты обратно не показывает — значения берутся там же, где были
получены. Токен публикации, по словам самого инструмента: @BotFather → бот
Аи → Serverless → CLI Access → Access token.

| Строка | Зачем | Без неё |
|---|---|---|
| `TGCLOUD_HEART_TOKEN` | публиковать | только будильник |
| `AI_PROVIDER_KEY` | ключ модели, вписывается в код на время публикации | публикации не будет |
| `OWNER_TG_ID` | кому Аи пишет о поломках | годится, если владелец записан в `config.js` |
| `KEY_GIGACHAT`, `KEY_EXPLABS` | запасные мозги: имя после `KEY_` — `id` из `AI_PROVIDERS` (`docs/BRAINS.md`) | запасной провайдер спит |
| `KEY_CLOUDFLARE` | рисование, переводчик и ещё один запасной мозг: `ID аккаунта:токен` | не рисует; переводит запасным переводчиком |
| `KEY_TAVILY`, `KEY_EXA`, `KEY_YOU` | поиск в интернете («найди в интернете …» и когда сама не знает); спрашиваются в этом порядке | ищет по Википедии |
| `HEART_BRANCH` | за какой веткой следить | ветка, с которой склонирована папка |
| `ALARM_BOT_TOKEN`, `ALARM_CHAT_ID` | минутный будильник через канал | будильник раз в 10 минут через платформу |

Файл, созданный проверкой, уже закрыт от чужих глаз. Созданный руками —
закрыть: `chmod 600 ~/.heart.env`.

ID канала — строка `ABILITIES_CHANNEL_ID` в `tgcloud/lib/config.js`:
`grep ABILITIES_CHANNEL_ID ~/Ai/tgcloud/lib/config.js`.

## 3. Проверить и запустить

```bash
cd ~/Ai
bash scripts/phone.sh check
nano ~/.heart.env
bash scripts/phone.sh check
bash scripts/phone.sh
```

Первая проверка создаёт файл ключей и перечисляет, чего не хватает, — строки
с ✗. Вторая, когда значения вписаны, должна кончиться словами «Готово к
работе». Только после этого — последняя строка.

`check` ничего не публикует: смотрит, на месте ли программы, принят ли токен
платформой, видит ли бот-будильник канал. Ключей на экран не выводит.
`check tests` заодно прогонит тесты — узнать, работают ли они на этом телефоне.

Ключи читаются один раз, при запуске: поменяли файл — остановите скрипт
(Ctrl+C) и запустите снова.

Первый запуск публикует сразу. Что считать успехом — не строку в Termux, а
сообщение от Аи: «🤍 Хозяин, я обновилась: …» с номером сборки и
самопроверкой. Затем «статус» в боте: «Сердце: …» с тем же номером.

## 4. Когда он публикует

**Новый номер сборки — новая публикация.** Скрипт сравнивает `BUILD` в
`tgcloud/lib/heart.js` с тем, что публиковал в прошлый раз. Коммит без нового
номера — работа в процессе: папка обновится, в живого бота ничего не уйдёт.
Так недоделанное не попадает к людям.

Нужно иначе — строка `HEART_DEPLOY_ON=commit` в файле ключей: тогда
публикуется каждый коммит. Опубликовать руками, не дожидаясь номера:
остановить цикл (Ctrl+C) и `bash scripts/phone.sh deploy`.

Порядок (с 0.36.3): малый запрос к платформе — есть ли связь → тесты (один
раз на коммит) → копия коммита в `~/.heart/stage`: из неё убираются
комментарии, в неё вписываются ключи → репетиция обработчиков в облаке →
публикация → схема базы → проверка вебхука → пробуждение. Папка `~/Ai` при
этом не меняется; копия с ключами после любого исхода стирается, а после
удачи — становится слепком опубликованного, уже без ключей.

**Мини-приложение «Комната» (с 0.38.0).** В порядке три новых шага: после
репетиции обработчиков — репетиция функции комнаты; код уходит вместе с этой
функцией; после проверки вебхука — отдельной отправкой страница комнаты (папка
`miniapp/`). Адрес страницы называет платформа, и телефон передаёт его Аи
вместе с пробуждением: по нему она ставит кнопку «🚪 Открыть комнату» под
ответом и кнопку «Комната» в меню. **Комната — надстройка: что бы ни вышло с
её шагами, сам бот публикуется.** Не прошла репетиция функции, платформа не
приняла функцию или страницу, оборвалась связь на странице — бот на новой
сборке, комната отвечает словами, а вам приходит одна весть: «⚠️ Телефон:
сборка … опубликована, но мини-приложение «Комната» — нет: <причина>». Страница
отправляется один раз, вместе со сборкой; повторить — `bash scripts/phone.sh
deploy` (раздел 8). В Termux при удаче — строка «✓ Мини-приложение «Комната»
опубликовано: кнопка под ответом на «зайду к тебе» и в меню бота».

**Почему копия и почему без комментариев.** Инструмент отправляет в облако
весь код одним запросом. 17.11.2026 запрос перешёл за три миллиона байт, и
облако обрывало передачу: сборки 0.36.0–0.36.2 не опубликовались ни разу, хотя
связь была. Комментарии — пятая часть кода; облаку они не нужны, а в
репозитории остаются. В Termux об этом строка: «Код для облака: 2450 КБ одним
запросом (с комментариями было бы 2990 КБ)».

**Нет связи с платформой — это не неудача сборки.** Малый запрос не прошёл —
тесты не гоняются, попытка не считается; скрипт пробует снова через три
минуты. Владельцу он пишет, только если связи нет четверть часа.

**Оборвалась отправка кода — телефон выясняет сам, в чём дело.** Сначала малый
запрос (есть ли связь), потом контрольная репетиция той сборки, что уже в боте
(берёт ли платформа прежний код). Итог — словами после «Причина:» (раздел 8).

**У каждого запроса к платформе предел времени** — семь минут
(`HEART_CALL_LIMIT`, секунды): зависшее соединение дом больше не держит.
17.11.2026 первая попытка провисела двадцать четыре минуты.

**Пока идёт публикация, будильник бьёт**: тесты и отправка занимают минуты, и
на это время удары в канал шлёт помощник. Раньше будильник в эти минуты
молчал.

**Кто пишет «⚠️ Телефон: …».** Скрипт на телефоне — голосом второго бота, того
самого, что бьёт будильник в канал. Аи о несостоявшейся публикации знать не
может: она в облаке, на прежней сборке. Одна весть на коммит.

Публикуется только вершина ветки — так, как она лежит в GitHub. Не вышло
свериться с GitHub или в папке есть несохранённые правки — публикации в этот
раз нет.

Неудача не повторяется без конца: три попытки на один коммит подряд, дальше —
раз в час (причина бывает и временной: связь). Новый коммит или перезапуск
скрипта — сразу ещё попытка. Нехватка настройки (нет ключа, образец вместо
ключа) попыткой не считается: скрипт говорит о ней и ждёт.

## 5. Чей голос у будильника

Платформа будит сердце только обновлением из Telegram, а о собственных
сообщениях бот обновлений не получает. Поэтому в канал «Мост» раз в минуту
должен говорить кто-то другой.

- **Тестовый бот — да.** Он уже есть, нужен только его токен
  (@BotFather → `/mybots` → бот → API Token) и права админа в канале «Мост»:
  публиковать и править сообщения. Его собственный код при этом не важен и не
  меняется: скрипт говорит от его имени сам.
- **Будущая Юи** — можно будет вписать её токен вместо тестового, но
  незачем: будильнику всё равно, чей голос.
- **Второй аккаунт — нет.** Аккаунту вместо одной строки нужен отдельный
  клиент Telegram на телефоне; его сессия — полный доступ к аккаунту; за
  автоматику Telegram аккаунты ограничивает. Его дело — быть «вторым
  человеком» на проверках: игры вдвоём, поведение с чужими.
- **Без голоса вовсе.** Не вписывать `ALARM_*` — тогда скрипт будит сердце
  сам, через платформу. Каждый такой удар отправляет туда весь код, поэтому
  он редкий: раз в 10 минут (`ALARM_RUN_EVERY`, секунды). Бьёт он тем кодом,
  который опубликован с этого телефона (его слепок лежит в `~/.heart/live`),
  а не тем, что успело прийти в папку: недоделанный коммит в живую базу не
  ходит. До первой публикации с этого телефона такого удара нет.

Одно сообщение «⏰ дата время» в канале — это и есть будильник: оно не
множится, а правится.

## 6. Чтобы телефон не усыпил

- Настройки → Приложения → Termux → Батарея → **без ограничений**.
- Телефон на зарядке и в Wi-Fi.
- Скрипт сам берёт `termux-wake-lock`; в шторке висит уведомление Termux —
  не смахивать.
- Автозапуск после перезагрузки: приложение Termux:Boot и файл
  `~/.termux/boot/heart.sh`:

```bash
#!/data/data/com.termux/files/usr/bin/bash
termux-wake-lock
cd ~/Ai && bash scripts/phone.sh >> ~/.heart/boot.log 2>&1
```

## 7. Команды

| Команда | Что делает |
|---|---|
| `bash scripts/phone.sh` | работать: публикация и будильник, пока не остановят |
| `bash scripts/phone.sh check` | проверить настройку |
| `bash scripts/phone.sh deploy` | опубликовать сейчас то, что лежит в ветке |
| `bash scripts/phone.sh tick` | разбудить сердце один раз |
| `bash scripts/phone.sh once` | один круг: проверить ветку, опубликовать, разбудить |
| `bash scripts/phone.sh events` | спросить платформу, какие события она отдаёт коду (нужно для «секретаря»); ничего не публикует, бота не трогает, токен не нужен; можно запускать рядом с работающим домом |

Журналы — в `~/.heart/`: `phone.log` (что происходило), `deploy.log`
(последняя публикация), `tests.log` (последние тесты). Там же `live/` —
слепок опубликованного кода (без комментариев и без ключей): им бьёт
будильник без второго бота и им же идёт контрольная репетиция; `stage/` —
копия для облака, живёт только во время публикации; `tested` — какой коммит
уже прошёл тесты; `waiting` — с какого часа нет связи с платформой.

### Если Аи пишет о моделях

Это вести от неё самой, в личку. С 0.32.1 у каждой своя причина и свой совет;
подробно — [BRAINS.md](BRAINS.md), «Когда отвечает запасная».

| Начало вести | Что это | Что делать |
|---|---|---|
| «ℹ️ Хозяин, к сведению — это не поломка» | у основной модели вышел дневной лимит или он на исходе; отвечает запасная | ничего: в вести назван час, когда основная вернётся |
| «△ … работает хуже» и «все модели упёрлись в лимит» | думать нечем, вопросы записываются и получат ответ позже | ничего; чтобы не повторялось — ключ ещё одного провайдера (раздел 2, строки `KEY_…`) |
| «△ … работает хуже» и «закрыта или снята у провайдера» | провайдер отключил модель | переслать весть в рабочий чат: имя заменит агент |
| «△ … работает хуже» и «нет связи» / «сегодня подвела … раз» | сбой у провайдера | обычно проходит само; держится дольше суток — сказать ей «проверь мозги» и переслать ответ в рабочий чат |
| «🚨 … сломалось» и «ключ … не принят» | ключ отозван или вписан с ошибкой | проверить названную в вести строку в `~/.heart.env`, затем `bash scripts/phone.sh deploy` |

Почему в последний раз отвечала запасная — «статус», строка «Запинка основной».

### Если новая сборка ведёт себя плохо

В `main` лежит последняя слитая сборка — та, на которой закончился прошлый
чат. Вернуть её:

1. остановить скрипт на телефоне (Ctrl+C);
2. в `~/.heart.env` поставить `HEART_BRANCH=main`;
3. `bash scripts/phone.sh deploy` — опубликует `main`; затем
   `bash scripts/phone.sh` — работать дальше на ней;
4. написать в рабочий чат, что пошло не так. Придёт исправление — вернуть в
   `HEART_BRANCH` ветку чата и перезапустить скрипт.

Телефона под рукой нет — то же делает кнопка: GitHub → Actions → Heart → Run
workflow → ветка `main`, `deploy` (тратит минуты Actions).

Пока PR #28 не слит, в `main` лежит старая сборка 0.20.97 без этого скрипта:
шаги 2–3 тогда не сработают, остаётся кнопка.

Таблицы базы у ветки те же, что у `main`. Записи, которые успела сделать
новая сборка, старая не знает и не читает. Вживую возврат не проверялся.

## 9. Слияние и новый чат

**Первый чат слит 16.11.2026**: PR #28, в `main` — сборка 0.35.1. Что сделать
на телефоне — абзац «После слияния» ниже; что написать новому чату — «В новом
чате».

Рабочий чат живёт в своей ветке. Телефон следит за той веткой, что названа
строкой `HEART_BRANCH` в `~/.heart.env`, и публикует из неё.

**Когда чат закончен — слить.** GitHub → Pull requests → нужный PR → «Merge
pull request». Само слияние ничего не публикует и минут Actions не тратит:
в боте уже стоит эта же сборка, её опубликовал телефон из ветки. Красная
проверка «Workers Builds: ai-bot-prod» слиянию не мешает: она красная и в
`main`, это проект Cloudflare, подключённый к репозиторию, а не этот код.

**После слияния** — в `~/.heart.env` поставить `HEART_BRANCH=main` и
перезапустить скрипт (Ctrl+C, затем `bash scripts/phone.sh`). Номер сборки тот
же, поэтому заново ничего не публикуется. Если этого не сделать, ничего не
сломается: Аи работает как работала, а телефон, когда прежнюю ветку удалят,
будет писать, что ветки нет.

**В новом чате** объяснять заново ничего не нужно. Первой строкой написать
«Прочитай AGENTS.md и продолжай» — и дальше, что сделать: порядок работы, ваши
решения и всё несделанное агент возьмёт из репозитория. Он работает в новой
ветке и после первого push называет её имя. Дальше — как удобнее:

- **как было** — вписать это имя в `HEART_BRANCH` и перезапустить скрипт:
  каждая новая сборка публикуется сама, проверяется вживую, а слияние — в
  конце чата;
- **осторожнее** — оставить `HEART_BRANCH=main`: в бота попадает только слитое,
  но проверить сборку вживую до слияния нельзя.

Ключи читаются один раз, при запуске: после правки файла скрипт нужно
перезапустить.

## 10. То же на ноутбуке

Git Bash, тот же файл `~/.heart.env`, те же команды. Локальные тесты там
выключены сами: на Windows они падают из-за среды, а не кода.
